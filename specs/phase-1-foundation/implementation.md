## Beginner Level

### What This Does

Scramble is an iPhone app that helps a family plan trips. Before this phase, the
project was just empty Xcode template code. After Phase 1, the app:

- Launches and shows two tabs at the bottom — **Trips** and **Master Lists**.
- Lets the user create a trip with a name, dates, and a handful of attributes
  (like "by plane", "rainy weather"), and add people to it.
- Stores everything on disk so it survives quitting the app, and syncs to the
  user's iCloud so other devices see the same data.
- Shows a trip in detail with a vertical "timeline" of seven phases (Weeks
  before, Day before, Departure day, During trip, Day before return, Return
  day, After trip), although the phases themselves are still empty —
  expanding them with checklists and packing items is the job of later phases.

### Why It Matters

Every later feature — the rules engine that auto-suggests items, the packing
sheet, sharing trips with family — depends on the data shape and infrastructure
that landed here. If we got the data model wrong, fixing it later would require
painful migrations of users' real data. Getting the foundation right means
each later phase is purely additive.

### Key Concepts

- **SwiftData**: Apple's modern database framework for Swift apps. We mark a
  class with `@Model` and SwiftData handles saving it to disk.
- **CloudKit**: Apple's cloud sync. When we tell SwiftData "use CloudKit",
  data syncs to iCloud automatically.
- **Theme**: A bundle of colours used everywhere in the app. Phase 1 ships one
  theme called "Midnight Atlas" with a dark and a light variant.
- **Trip attributes**: Tags the user picks for a trip (Duration: Short/Long,
  Transport: Car/Plane/Train, etc.). These will eventually drive the rules
  engine that decides which packing items belong on this trip.

### Implementation Approach

**Composition root.** `ScrambleApp` injects `ModelStore.shared` (a SwiftData
`ModelContainer`) and `.environment(\.theme, .midnightAtlas)` once at the root.
Every descendant view reads these via `@Environment(\.modelContext)` / `@Query`
and `@Environment(\.theme)`.

**Container resolution.** `ModelStore.shared` is a `@MainActor static let`
evaluated once. It consults an injectable `EnvironmentProbe` to decide which
configuration to use:
- Unit tests (`XCTestConfigurationFilePath` env var present),
  UI-test host (`-uitest 1` launch arg), or SwiftUI Previews
  (`XCODE_RUNNING_FOR_PREVIEWS=1`) → in-memory container with
  `cloudKitDatabase: .none`.
- Production → CloudKit `.private("iCloud.me.nore.ig.scramble")`. If that
  throws, fall back to local-only at the default location and `os_log` the
  failure with a `[ModelStore.fallback]` marker.

**Codable blobs.** Per Decision 10, attribute selections and item conditions
are stored as JSON-encoded `Data` blobs on the `@Model` classes
(`Trip.attributesData`, `MasterTaskItem.conditionsData`,
`MasterPackingItem.conditionsData`). A typed `attributes` / `conditions`
computed property bridges through `CodableBridge.{encode,decode}`, which logs
decode failures via `modelLogger.error` and falls back to a default. The
bridge helper lives in one file so the three call sites can't drift.

**Enum bridges (Decision 14).** `Phase`, `ItemSource`, `PackingState` are
stored as `String` raw values (`phaseRaw`, `sourceRaw`, `stateRaw`) with
computed bridges. This sidesteps CloudKit schema-promotion friction.

**Theme.** `Theme` is a value type holding `dark`/`light` `ThemeVariant`s plus
a `PersonPalette`. Call sites use `theme.variant(for: colorScheme)` to pick the
right variant. `PersonPalette.nextUnusedKey(among:)` returns a non-optional
`PaletteEntry`; when all 8 are taken it returns the first canonical entry and
the editor surfaces the duplicate-colour advisory mandated by AC 9.4.

**Auto-open on cold launch (AC 5.6, 5.7).** `TripsTab` runs a
`.task(id: "trips-tab-mount")` once on first appearance. It calls
`singleQualifyingTrip(in:today:calendar:)`, sets `didAttemptAutoOpen = true`
**before** appending to the path (guard ordering matters under iOS 26's
lazier body re-evaluation), and uses `@State` not `@SceneStorage` —
state restoration would persist the flag and break the requirement.

**Trip editor (AC 8).** Operates on a value-type `TripDraft` so cancel
discards the draft cheaply. On save, `TripPersistence.{create,apply}` resolve
the participant IDs through a `FetchDescriptor<Person>` lookup; any IDs that
no longer resolve (because another device deleted that person while the editor
was open) are dropped silently and the parent surfaces the count via a
transient toast. This matches Decision 15's tolerance for cross-device
person-delete races.

### Trade-offs

- **Codable blobs over typed properties.** Cannot filter trips by attribute in
  a SwiftData predicate — must fetch then filter in memory. Acceptable given a
  household's small dataset, and avoids a schema migration every time we add
  an attribute category.
- **`.deny` declared but UI is primary enforcement (Decision 16).** SwiftData
  iOS 26.4 does not throw on `save()` after deleting a `Person` with live
  references. We kept the `.deny` rule as documented intent + defense in
  depth; the authoritative guard is `TripEditorView.requestDelete` which
  inspects the inverse relationships before allowing the deletion.
- **Default CloudKit zone, not per-trip zones (Decision 9, supersedes
  Decision 8).** SwiftData has no public API to route records into per-trip
  custom zones. The original "one zone per trip" plan was unachievable
  without dropping SwiftData. Deferred to the CKShare phase as a one-time
  per-device data move.
- **One theme shipped but the structure supports many.** No theme picker UI;
  variant follows the system `colorScheme`. Adding a second theme later
  requires no call-site changes.

## Expert Level

### Technical Deep Dive

**Relationship topology.** Inverse declarations are colocated with the delete
rule on a single relationship. The owning side declares
`@Relationship(deleteRule:, inverse:)`; the non-owning side is a plain
`@Relationship var` with no arguments (declaring `inverse:` on both has
produced container-construction warnings in earlier Xcode releases).
The Decision 16 wrinkle: `Person.tripPackingItems` and
`Person.masterPackingItems` are declared as the owning side
(`@Relationship(deleteRule: .deny, inverse: \TripPackingItem.person)`) so the
SchemaTests can exercise the inverse traversal that the UI guard uses. This
diverges from design.md's "owning side only" wording for these two pairs;
the divergence is documented in Decision 16.

**JSON discriminator on `ItemConditions`.** The `indirect enum` (`.always`,
`.match`, `.all`, `.any`) implements `Codable` manually with a discriminator
key, so on-disk JSON is stable even if cases are reordered. The custom
encoder/decoder is exercised by a depth-bounded recursive generator in
`ItemConditionsTests.roundTripProperty` (depth ≤ 3 to avoid combinatorial
explosion).

**EnvironmentProbe isolation contract.** `ProcessInfo.processInfo` cannot be
mocked in-process. `EnvironmentProbe` wraps `environment: [String: String]` +
`arguments: [String]` as a `Sendable` value type, with `EnvironmentProbe.production`
reading `ProcessInfo`. Tests construct probes with synthetic values and assert
the `ModelStore.configuration(probe:)` branch selection. A separate
`AppLaunchUITests.testLaunchUsesInMemoryContainer` asserts the host-app side
wires up by reading a debug-only accessibility identifier
(`DebugAccessibilityID.modelStoreInMemory`) emitted on `RootView`.

**TripsTab `.task` re-fire guard.** `iOS 26`'s lazier `TabView` body
re-evaluation can fire `.task(id:)` twice in close succession. The
implementation sets `didAttemptAutoOpen = true` *before* mutating the
navigation path; if the task re-fires, the second invocation observes the
flag and returns early. `singleQualifyingTrip` itself is a free
`@MainActor` function, table-driven tested in `TripsTabPredicateTests`
across empty, one-qualifying, one-non-qualifying, two-qualifying, and the
exact-boundary cases.

**Tab bar visibility.** Trip Detail applies `.toolbar(.hidden, for: .tabBar)`
both on the view itself and inside `TripsTab.navigationDestination`. The
redundancy is intentional: design.md flags that every child view needs the
modifier; landing it on the destination edge is the belt-and-braces version.

**Phase node state machine.** `TripDetailView.state(for:today:start:end:calendar:)`
normalises today/start/end via `Calendar.startOfDay` and dispatches per phase.
`returnDay` returns `.current` on the exact end day; `afterTrip` returns
`.future` while `today <= end` and `.current` once strictly past — the spec
mandates only three distinguishable states (Decision 13), so "current" is
re-used for "currently in the after-trip phase" rather than introducing a
fourth state.

**Performance characteristics.** All hot paths in Phase 1 operate on small
collections (household-scale: ~few trips, ~few people). The two corners that
would compound at scale —
`TripPersistence.resolveParticipants` and `TripEditorView.orderedSelectedPeople` —
both use `Dictionary(uniqueKeysWithValues:)` lookups (O(N+M), not O(N·M)).
`Trip.attributes` is re-decoded on every body render that touches it
(`TripDetailView.chipRow`, `TripRow`); for the current chip count this is
negligible, but if condition sets grow significantly (rules-engine phase),
caching the decoded value in `@State` keyed off `attributesData` is the
pre-known mitigation.

### Architecture Impact

- **Single shared `ModelContainer`.** All views participate in one SwiftData
  context. Background contexts are explicitly not needed in Phase 1 (no
  batch jobs, no rules engine). The rules-engine phase may want to introduce
  one — `ModelStore.shared` is `@MainActor`, but the
  `nonisolated ModelStore.configuration(probe:)` factory is the seam for
  spinning up additional contexts.
- **`Theme` injection model is stable.** Adding a second theme is purely
  additive: declare it, expose a picker, write to `\.theme` from the picker.
  No call site changes needed.
- **VersionedSchema in place from day one.** `AppMigrationPlan` has zero
  stages now; the first real migration is a routine `MigrationStage` addition
  rather than a container-bootstrap refactor.
- **Decision 9 deferral creates a known future migration.** The CKShare phase
  will need to move trip-owned records (Trip, TripTask, TripPackingItem) from
  the default CloudKit zone into per-trip custom zones as a one-time
  per-device data move. This is bounded but non-trivial — `docs/agent-notes/persistence.md`
  flags it for the agent that takes that phase.

### Potential Issues

- **Cross-device `Person.colorKey` drift.** Two devices can edit the same
  person's `colorKey` independently; CloudKit's last-writer-wins applies.
  Acceptable in Phase 1; the colour is a per-theme palette key string and any
  unknown key renders as `.gray` (the `PersonAvatar` fallback).
- **`Person.initial` on empty `name`.** Returns `"?"` — both the SwiftData
  derived property and the SwiftUI render now share the same
  `String.firstGraphemeUppercased` helper, so the fallback can't drift.
- **CloudKit schema promotion is a manual step.** The first production deploy
  requires promoting the dev schema via the CloudKit Dashboard. Until then,
  TestFlight builds silently fall back to local-only and `os_log` the
  `[ModelStore.fallback]` marker. Post-deploy Console.app inspection is the
  current observability surface.
- **AC 9.7 UI guard is the only enforcement of person-delete denial.** A
  direct programmatic `context.delete(person)` from any path that bypasses
  the editor would not be blocked (Decision 16). Phase 1 has no such path,
  but future contributors must include the reference check at any new delete
  call site.
- **`@SceneStorage` regression risk.** A well-meaning contributor "improving"
  navigation persistence by switching `didAttemptAutoOpen` from `@State` to
  `@SceneStorage` would silently break AC 5.7. A code-review-visible comment
  on the declaration in `TripsTab.swift` flags this.

### Implementation Gaps vs Spec

1. **Design.md vs Decision 16 inverse-side wording (NICE-TO-HAVE).** Design.md
   says "Inverse declared on owning side only (`Trip.participants`, …,
   `TripPackingItem.person`, `MasterPackingItem.person`)". The implementation
   per Decision 16 places `inverse:` on `Person.tripPackingItems` and
   `Person.masterPackingItems`. The decision log is the source of truth;
   design.md remains the laggard. Updating the wording in design.md is
   pure bookkeeping.

2. **Test coverage gaps (NICE-TO-HAVE).** No explicit unit assertions for
   AC 4.1/4.4/4.5 (root TabView shape, session-only tab selection, default
   selected tab), AC 5.1/5.2 (Active vs Previous sectioning at the UI level),
   AC 7.1/7.2 (segmented control + placeholder), or
   `TripDetailView.state(for:...)` table-driven coverage. Each AC is exercised
   indirectly by `RootNavigationUITests` / `TripCRUDUITests`, but a dedicated
   unit test for the phase state machine in particular would prevent
   regressions in the boundary cases (today = start, today = end).

3. **AC 9.4 duplicate-color advisory + AC 9.3 default-color assignment
   (NICE-TO-HAVE).** Implemented in `PersonEditor`; no unit test for the
   editor-level wiring. `PersonPalette.nextUnusedKey` itself is covered.
